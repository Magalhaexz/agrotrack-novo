# SUPABASE LOTES + FUNCIONARIOS Schema Fix (HERDON)

## 1) Causa raiz
Hoje o HERDON tem um caminho de sincronizacao em lote e reconciliacao dedicado apenas para `fazendas` (`syncFazendasWithCloud`).

Para `lotes` e `funcionarios`:
- nao existe rotina equivalente de sincronizacao/manual merge por modulo;
- nao existe reconciliacao por `metadata.local_id` + `cloud_id` como em fazendas;
- o app depende de `create/update/deleteOperationalRecord` (tentativa direta na tabela), caindo para local quando ha erro de schema/RLS/config/rede;
- a arquitetura atual permite que Fazendas sincronize explicitamente, enquanto Lotes/Funcionarios ficam sem pipeline dedicado de sync e sem bootstrap de schema validado para esses modulos.

## 2) Estrategia de modelagem cloud
- `id`: PK bigint identity (ID cloud canonical).
- `owner_user_id`: `uuid not null references auth.users(id)` para isolamento por usuario.
- `cloud_id`: `uuid` estavel para rastreio externo e integracoes (unico).
- `metadata`: `jsonb` para guardar `local_id`, origem, auditoria de sincronizacao e compatibilidade evolutiva.
- `created_at` / `updated_at`: `timestamptz` com trigger de auto-update.

## 6) Trigger de `updated_at`
```sql
create or replace function public.set_current_timestamp_updated_at()
returns trigger
language plpgsql
as $$
begin
  new.updated_at = timezone('utc', now());
  return new;
end;
$$;

drop trigger if exists set_lotes_updated_at on public.lotes;
create trigger set_lotes_updated_at
before update on public.lotes
for each row
execute function public.set_current_timestamp_updated_at();

drop trigger if exists set_funcionarios_updated_at on public.funcionarios;
create trigger set_funcionarios_updated_at
before update on public.funcionarios
for each row
execute function public.set_current_timestamp_updated_at();
```

## 7) RLS (usuarios autenticados)
```sql
alter table public.lotes enable row level security;
alter table public.funcionarios enable row level security;

create policy "lotes_select_own"
on public.lotes
for select
to authenticated
using (auth.uid() = owner_user_id);

create policy "lotes_insert_own"
on public.lotes
for insert
to authenticated
with check (auth.uid() = owner_user_id);

create policy "lotes_update_own"
on public.lotes
for update
to authenticated
using (auth.uid() = owner_user_id)
with check (auth.uid() = owner_user_id);

create policy "lotes_delete_own"
on public.lotes
for delete
to authenticated
using (auth.uid() = owner_user_id);

create policy "funcionarios_select_own"

create policy "funcionarios_insert_own"

create policy "funcionarios_update_own"
```

## 8) Estrategia `metadata` / `local_id`
- Ao inserir via app, preencher `metadata.local_id` com o `id` local legado quando aplicavel.
- Preservar campos de auditoria de origem em `metadata` (ex.: `synced_from`, `synced_at`).
- Usar `metadata.local_id` para reconciliacao quando `id` cloud divergir do `id` local.
